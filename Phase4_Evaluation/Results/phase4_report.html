Phase 4 · Retrieval evaluation

The Fine-Tuning Reversal

Two benchmarks, six systems, 343 labelled questions. The off-the-shelf embedding model retrieves Qur'anic verses roughly twice as well as either model this project fine-tuned — and neither hallucination guardrail, measured for the first time, does what it was built to do. The retrieval fix has since been adopted and independently verified in the live system.

Benchmarks AyaTEC · QRCD Corpus 6,236 verses Test Wilcoxon signed-rank, paired Status fix verified in the 22–23 Aug re-run

The recommendation

Drop the fine-tuned model. Use base GATE-AraBert-v1 over a verses-only index.

It is significantly better on both benchmarks, on every metric, and it is also the simpler system — no training run, no tafsir index, no hybrid fusion layer. The improvement comes from removing work, not adding it.

The fix was adopted — and it checks out

Phases 1–3 were re-run on 22–23 August. This section verifies what that re-run actually used, rather than taking it on trust.

The rebuilt index carries the recommendation in its own source: "Base, untrained GATE-AraBert-v1 significantly outperforms both … Default model is now the base HF model, not the local fine-tuned checkpoint." It holds 6,236 entries, all verses, no tafsir — median passage length 55 characters, against 367 before, with the longest previously reaching 72,681 characters through a 64-token window.

To confirm the running system matched its configuration, the ten demonstration queries were re-issued against each candidate setup and the resulting similarity scores compared with those recorded in the re-run's own output files.

Worth noting

Confidence rose as relevance fell

For التوبة والاستغفار ("repentance and seeking forgiveness"), the corrected system returns five relevant verses at similarity 0.71. The fine-tuned system returns five consecutive tafsir passages from a single surah — at 0.77.

The discarded model was more confident and less useful. Similarity score and relevance moved in opposite directions, which is the clearest single illustration of why the fine-tuning failed.

Not propagated

The corrected file did not travel with the fix

Phase 2 and Phase 3 still carry the old b6_build_index_and_retrieval_api.py — byte-identical to each other, still defaulting to ./b5_real_finetuned. The runs overrode it, so the results are sound, but the archived folders would not reproduce them.

Why fine-tuning hurt

The training data was built from verse ↔ tafsir pairs — 12,358 triplets pairing each verse with Ibn Kathir's commentary on it. The deployed task is question → verse.

So the objective and the task were misaligned. The model was optimised to pull verse embeddings toward classical exegetical prose, while real queries arrive as modern Arabic questions. Two epochs of that moved the embedding space away from the geometry retrieval actually needed.

The ablation supports this reading directly: the fine-tuned models retrieve tafsir passages readily and verses poorly, which is exactly what they were trained to do.

Supporting findings

Each was measured on the same benchmarks with the same protocol.

Negative result

Indexing tafsir makes retrieval worse

Tafsir-only retrieval scores Recall@10 of 0.0120 — near noise. Removing tafsir from the v1 index raised Recall@10 by 45%, from 0.0422 to 0.0610. Half the index was crowding out the verses that hold the answers.

Negative result

Chunking the tafsir did not rescue it

The model truncates at 64 tokens while tafsir passages run to a median of 5,298 characters, so 100% of passages exceed the window and only ~5% of each is ever seen. Splitting them into 250-character windows that fit — 250,356 index entries — made retrieval four times worse (Recall@10 0.0197, p = 8.8e−07).

Classical exegesis fragments share little vocabulary with modern questions. They act as distractors at any granularity.

Methodological

Similarity score is not a relevance measure

The project's existing diagnostic ranked systems by cosine similarity to the top result. On that measure v1 beat v2. On relevance against labelled answers, v2 beats v1 significantly. A high score against a generic chapter heading outranks a lower score against the correct verse.

This is why the quality of the pipeline could not be assessed before now.

Replicated

The v2 augmentation did work — relative to v1

Adding AyaTEC data improved on v1 significantly (Recall@10 p = 0.0074, HitRate@20 p = 2.4e−04). That effort was sound. It simply started from a damaged baseline and never closed the gap to the untrained model.

Two bugs found while verifying

Neither was known. Both were found by trying to reproduce the re-run exactly, and both have one-line fixes.

Eight of the ten queries reproduced. The two that did not turned out to be separate defects rather than noise.

Bug · free to fix

Every search has been running at hnswlib's minimum accuracy

load_index() never calls set_ef, so a freshly loaded index sits at the library default of ef = 10. That is the size of the candidate list HNSW explores; at 10 the search is approximate enough to miss the true nearest verse.

Re-issuing the failing query at ef=10 reproduced the re-run's recorded score to 1.2 × 10−7, confirming the diagnosis. Across all 174 AyaTEC questions, ef=10 returns the wrong nearest verse on 37 of them — 21.3%. At ef=256 that is zero.

Bug

Query refinement repeats itself

Asked about العدل في الإسلام ("justice in Islam"), the agent iterated three times and produced العدل في الإسلام قسط انصاف قسط انصاف — the same two synonyms appended twice. It re-adds expansion terms each round instead of tracking what it has already added.

Retrieval got worse as it iterated: top similarity fell from 0.51 to 0.46. The loop is currently a cost with no measured benefit.

Setting ef=256 raises Recall@10 by 18.9%, HitRate@10 by 17.9% and MRR by 18.9%. Metrics saturate there, so no tuning is required. It is a search-time parameter: no retraining, no reindexing, no change to stored data — a single line after load_index().

Because every result in this report was produced through the same unset parameter, the reported figures understate the system's actual retrieval quality. The comparisons stand — all six systems were measured under identical conditions — but the absolute numbers are a floor, not a ceiling.

Does it admit when it doesn't know?

33 AyaTEC questions are labelled zero_answer — the Qur'an does not answer them. Answering anyway is the hallucination this project is named after.

Three conditions isolate what the guardrail contributes: plain RAG, RAG told explicitly to reply INSUFFICIENT when the verses don't cover the question, and that same instruction plus a refusal gate when top retrieval similarity falls below 0.62. Negative result

The abstention instruction changes nothing

Refusal on unanswerable questions is 0.424 with and without it — the same 14 of 33. What the instruction did change was over-refusal, which rose from 22% to 35%. It made the system more cautious on questions it could answer, and no more cautious on the ones it couldn't.

Negative result

The similarity gate is not detection

At 0.62 it refuses 97% of unanswerable questions and 92% of answerable ones — a five-point gap. It is not identifying anything; it is refusing almost everything.

Measured ceiling

No threshold on retrieval score can work

Five candidate signals were tested as answerability classifiers over all 207 questions. The best, top-1 similarity, reaches AUC 0.634; margin, count-above-threshold and top-10 spread all sit at chance. A guardrail needs roughly 0.8 to be worth shipping.

Sweeping all 25 thresholds, the best operating point is 0.411 — refusing 42.4% of unanswerable questions at 20.7% over-refusal. That is the ceiling for any rule of this shape.

The telling coincidence

The gate's best case is what the model already does

Plain RAG, with no instruction and no gate, refused 42.4% of unanswerable questions at 21.7% over-refusal. The best achievable threshold gives 42.4% at 20.7%.

The two are the same point. The sufficiency gate cannot improve on the model's own implicit judgement — it can only degrade it, which at 0.62 is what it does.

One caveat on the hallucination count

The "citing a verse never retrieved" row measures ungroundedness, not falsehood. One flagged case cited 4:34 for a question about the treatment of wives — the correct verse, recalled from the model's own training rather than from context. A genuine failure looks different: asked where the first qibla was, the system cited eight unrelated verses including 12:39 and 69:43.

Both are ungrounded; only the second is a hallucination in the ordinary sense. The write-up should separate them.

Some gold labels are also stricter than they look. من هي ملكة سبأ؟ is labelled unanswerable because the Qur'an never names the Queen of Sheba — the system cited 27:23 and 27:42, which discuss her without naming her. That answer is defensible.

The other guardrail fails too

Phase 3 ships a second, unrelated mechanism: extract triples from the answer and from the context, build graphs of both, and reject when their structural mismatch exceeds a tolerance. It was evaluated here for the first time.

The 23 August run covers ten queries. Each answer was scored against a simple criterion — does every verse the answer cites actually appear in the passages that were retrieved? The guardrail's own pipeline was re-executed and reproduced its stored mismatch scores exactly, to 0.00e+00, so what follows measures the real component and not an approximation of it.

Negative result

It verifies two answers, and one of them is wrong

Of ten answers the guardrail passed two. One of those two cites 69:51, 70:26 and 74:47 — none of which were retrieved. Meanwhile it rejected two answers whose citations were entirely grounded.

Rank agreement between the mismatch score and the share of ungrounded citations is +0.12, near zero. Mean mismatch is 0.705 for clean answers and 0.818 for ungrounded ones: the distributions almost entirely overlap.

Negative result

Calibration does not rescue it

The new f2 script has a genuinely good idea behind it: build labelled examples from QRCD by pairing each gold answer with its real passage (grounded) and with an unrelated one (hallucinated), so nobody needs theological expertise to label them.

It doesn't work, and the reason matters. On 80 such examples the two classes overlap — 12 of 40 genuinely grounded pairs score the maximum mismatch of 1.0, and 3 hallucinated pairs score 0.0. The triple-extraction step simply fails on much of the Arabic. Calibration therefore lands on the degenerate tolerance 0.00, which performs exactly as well as the guessed 0.50: no better than always guessing.

Inconsistency

The two grounding checks disagree flatly

On overlapping queries, Phase 2 reports 9 of 10 answers grounded while Phase 3 verifies 2 of 10. Both cannot be right. Separately, all ten Phase 2 answers came back in English despite Arabic questions and an Arabic-only specification; Phase 3's answers are correctly in Arabic.

What this does and does not license

The obvious replacement is a direct check: every [verse_key] in an answer must appear in the retrieved context. It is trivial, needs no calibration, and cannot be evaded by a graph-alignment quirk.

But its apparent perfection here is definitional, not empirical — that rule is the criterion the guardrail was scored against, so it is right by construction and this evidence cannot be used to claim it wins. The honest statement is narrower: the structural guardrail performs no better than chance at catching ungrounded citations, so a direct check is at least as good and far simpler.

A citation check also catches only one failure mode. An answer that cites a retrieved verse but misreads it passes cleanly. Neither guardrail addresses that, and neither claims to.

What this does not show

  • That fine-tuning cannot work here. Only that fine-tuning on verse↔tafsir pairs does not. Training on question→verse pairs is untested and is the obvious next experiment.
  • That the system is good. Base reaches 20% of the achievable Recall@10 on AyaTEC. It is the best of six, not strong in absolute terms.
  • That QRCD gold labels are exact. They were recovered from passage ranges, so a question's gold set spans a whole passage — a median of 18 verses. Compare systems to each other on that benchmark, not to 1.0.
  • That abstention is settled at scale. 33 unanswerable questions is a small set, and the answerable control was sampled at 60. The direction is clear; the exact rates are not precise.
  • That a different generator behaves the same. Only allam-2-7b was tested. Groq has retired every Llama model, so the generator was chosen from what remains available.
  • That the structural guardrail is settled. It was evaluated on the ten demonstration queries, of which nine carry citations. That is enough to show it does not beat a majority baseline; it is not enough to characterise it precisely.
  • That absolute retrieval numbers are final. Every figure here was produced at ef=10. Raising it lifts Recall@10 by roughly 19% across the board, so the reported values are a floor. Relative comparisons are unaffected.

An operational problem, separate from the findings

Groq withdrew llama-3.3-70b-versatile, which every project notebook hardcoded — Phase2_Laiba_Complete_Integration, Phase3_Guardrail, Complete_Fix_Phase1_Phase3, generate_phase2_dashboard.py. All four fail with a 404 as written.

The August re-run evidently worked around this, but no record of how survives. No model identifier appears anywhere in the Phase 2 or Phase 3 output folders; d2_cot_prompting.py takes the language model as an injected callable, so the choice lived in a driver notebook that was never saved to Drive. The outputs exist; the code that produced them does not.

Nobody can currently reproduce the generation results, and the person who ran them is the only remaining source for which model was used. That is worth recovering while it is still recoverable.

Next

  • Set ef=256 after loading the index. One line, no retraining, ~19% on every retrieval metric. Nothing else on this list is close to that ratio of benefit to effort.
  • Propagate the corrected b6 into Phase 2 and Phase 3, and record the generator's model identifier in version control. Both folders currently default to the discarded fine-tuned model.
  • Replace the structural guardrail with a direct citation check — every cited verse must appear in the retrieved context — and drop the mismatch tolerance rather than calibrating it further.
  • Fine-tune on question→verse pairs using QRCD's train split, evaluating on QRCD test and AyaTEC. This tests the misalignment mechanism directly and remains the strongest open experiment.
  • Replace the answerability signal. Retrieval score is exhausted at AUC 0.634. Worth testing: a dedicated LLM sufficiency call, a classifier over retrieved passages, and agreement between two independent retrievers.
  • Turn the ten-query demonstrations into evaluations. Both guardrail conclusions currently rest on nine usable answers. The retrieval work already runs at 174 questions; the generation side should match it.
  • Fix query refinement or remove it. It duplicates its own expansion terms and made retrieval worse on the one query where it engaged.
